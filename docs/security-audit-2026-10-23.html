一、高危漏洞（P0，建议立即修复）

高危 · 已修复1. 导入接口文件名路径穿越 → 任意文件写入（3 处）

backend/routes/devices.js:187（import-preview）｜backend/routes/racks.js:704（import-preview）｜backend/routes/racks.js:817（import）

三处上传接口把客户端提供的原始文件名直接拼进落盘路径：path.join(tempDir, \`preview_${Date.now()}_${csvFile.name}\`)。express-fileupload 不过滤文件名，攻击者可将 filename 设为 ../../../../xxx.js，经 path.join 规范化后跳出 temp 目录，实现任意路径、任意内容的文件写入。

已实测验证：恶意文件名 ../../../../Windows/Temp/evil.txt 的落盘结果为 E:\IDC\idc_assest\Windows\Temp\evil.txt，确认跳出目标目录。

利用条件与危害升级：需要已认证且具备 device:create / rack:create 权限。但写入内容完全可控（CSV/Excel 原文），可覆盖 backend 下任意 .js 文件；若服务以 nodemon 运行（npm start 即 dev 模式，watch 整个目录），写完 routes/*.js 会立即热重载并执行 → 直接 RCE；即使生产用 node server.js，也可在下次重启时生效。同项目 devices.js:1184 的正式导入端点已用 path.basename + 严格相等校验修复，说明团队知道正确写法，只是漏掉了预览端点。

修复建议：统一复用 devices.js:1184 的防护模式——const safe = path.basename(file.name); if (!safe || safe !== file.name) 拒绝；更稳妥的做法是干脆丢弃原始文件名，统一用随机文件名（如 background.js:81 的写法，该项目里已有范本）。建议同时排查全部 file.mv() 调用点。

高危 · 已加固2. xlsx（SheetJS 0.18.5）原型污染 + ReDoS，npm 无安全版本

backend/package.json:77（xlsx ^0.18.5）｜使用点：backend/routes/racks.js、backend/routes/tickets.js、frontend 6 个页面（PortManagement、CableManagement、ConsumableManagement 等）

npm audit 对 xlsx 报出 2 个 high 漏洞（Prototype Pollution、ReDoS），且 fixAvailable: 无——0.18.5 是 npm 上最后一个版本，官方已将新版改为 CDN 分发，npm audit 永远无法自动修复。该库直接解析用户上传的 Excel，恶意构造的工作簿可通过 __proto__ 相关键污染 Object.prototype，可能引发权限判断异常、数据篡改等连锁反应；ReDoS 可被超长单元格拖死进程。

修复建议（三选一）：① 后端替换为 exceljs（维护活跃、无同类 CVE）；② 升级 SheetJS 至官方 CDN/最新发行版并锁定来源；③ 短期缓解：限制上传文件大小与单元格数量、解析前做基础结构校验。不建议长期停留在 0.18.5。

高危 · 已修复3. 注册接口"首用户抢占管理员"

backend/routes/auth.js:55-118（register）

POST /api/auth/register 完全公开，且逻辑为：User.count() === 0 时，首个注册用户直接获得 admin 角色和所有权限。这意味着系统部署后、正式管理员注册前的窗口期内，任何能访问到端口的人都可以抢注成为超级管理员。对于部署在公网或大内网的系统，这是一个现实的账户接管面。

修复建议：① 安装流程（install.js）中强制交互式创建首个管理员，注册接口对"首用户"场景关闭或要求一次性令牌；② 或增加"允许自主注册"的系统开关，默认关闭；③ 已部署的系统如尚未注册管理员，请立即注册并检查现有用户列表。

二、中危问题（P1，建议尽快处理）

中危4. POST /api/maintenance/disable 无需认证

backend/server.js:427-450

公开路径白名单 PUBLIC_PATHS 包含 /maintenance，而 isPublicPath 使用 startsWith 前缀匹配，导致 /api/maintenance/status 和 /api/maintenance/disable 双双跳过 authMiddleware——任何未认证用户都可以关闭维护模式。单独看破坏面有限（只是让普通用户恢复登录），但属于明确的未授权操作，且说明前缀匹配的白名单机制容易误伤。

修复建议：将 disable 移出公开前缀匹配（精确匹配 status 一个路径即可），或给 disable 单独加管理员鉴权。

中危5. 请求日志记录完整 URL，token 可落盘

backend/middleware/requestLogger.js:39（url: req.originalUrl）｜backend/middleware/auth.js:109（req.query.token）

requestLogger 把 req.originalUrl（含 query string）写入日志；而认证中间件支持从 ?token=xxx 取令牌。如果任何客户端/调用方用 URL 传 token，JWT 会明文落盘到 logs/ 目录，日志又常被备份、外发或纳入 ELK，扩大泄露面。

修复建议：① 取消 query.token 传参方式，统一走 Authorization 头（确有下载等场景需要的话，改为一次性签名 URL）；② 日志记录 url 前对 query 中的 token 字段脱敏。

中危6. /temp 静态目录公开暴露 + 临时文件可预测

backend/server.js:28（app.use('/temp', express.static('temp'))）｜backend/routes/racks.js:704/817

/temp 未做任何鉴权即静态暴露。racks 导入的临时文件名为 ${Date.now()}_${原始文件名}，时间戳可预测、可枚举；且 racks.js:716-722 解析失败的分支直接 return 400 没有清理临时文件（成功分支有 unlink）。未认证用户可枚举下载残留的导入 Excel（含资产明细数据）。若高危漏洞 1 被利用写入的文件落在可经 URL 到达的位置，也会由此读取。

修复建议：临时文件统一放系统临时目录或 uploads 外的不可路由位置；确需 /temp 时加鉴权中间件；文件名改随机不可预测值；解析失败分支也补 unlink。

中危7. 登录无 IP 级限速，账户锁定可被武器化

backend/routes/auth.js:285-321

登录有账户锁定（失败 N 次锁 30 分钟，.env 配 3 次/15 分钟），但没有基于 IP 的速率限制：① 攻击者可故意连续输错密码把任意已知用户名锁死，构成账号级 DoS；② loginCount 的"读取-累加-保存"存在并发竞态，瞬时并发请求可能多搏到几次机会；③ 无法缓解对单一密码的分布式慢速尝试。

修复建议：引入 express-rate-limit，按 IP + 用户名双维度限流（如每 IP 每分钟 10 次登录尝试）；账户锁定增加"仅对密码错误计数、不影响账号正常使用"的降级策略或加验证码。

中危8. 错误响应直接回显内部 error.message

backend/routes/backup.js:545、632 等多处（grep 全库约 30+ 处 error: error.message）

大量接口在 catch 中把 error.message 原样返回客户端，可能泄露内部路径、SQL 片段、依赖行为等侦察信息，降低攻击成本。

修复建议：生产环境统一返回"服务器内部错误"通用文案，详细错误只进服务端日志（可按 NODE_ENV 区分）。

中危9. axios 1.x 存在 SSRF 与认证绕过 CVE（可小版本修复）

backend/package.json:48（^1.13.6）、frontend 同（直接依赖）

audit 报 axios 1.0.0–1.19.0 两个 high：NO_PROXY 主机名规范化绕过导致 SSRF；validateStatus 合并策略的原型污染可导致认证绕过（错误响应被当作成功）。后端 axios 用于 Redfish 采集等外呼场景，SSRF 面真实存在。

修复建议：npm update axios 升至 ≥ 1.19.1（minor 升级，无破坏性变更）。

中危10. CORS 全开 + 缺少安全响应头

backend/server.js:25（app.use(cors())）｜全项目无 helmet

cors() 默认允许任意源跨域调用。当前令牌走 Authorization 头且存 sessionStorage（非 cookie），浏览器不会自动携带凭据，实际风险被压低；但全开 CORS 意味着任何网页都可以尝试调用 API，为未来的凭据处理变化埋雷。同时项目没有使用 helmet，缺少 X-Content-Type-Options、X-Frame-Options、CSP 等基础响应头。

修复建议：生产环境配置来源白名单（cors({ origin: [...] })）；引入 helmet 并配置 CSP；静态目录加 X-Content-Type-Options: nosniff。

五、做得好的地方（本次审计确认无问题）

  • 密钥管理干净：.env、remote-backup-configs.json 均在 .gitignore 中，git 未跟踪任何敏感文件；根目录残留的 idc_management.db 也未被提交；JWT_SECRET（88 位）、SMTP_SECRET_KEY 强度充足，生产强制 ≥32 位校验。
  • 敏感凭据加密存储：设备 BMC 密码、SMTP 密码、远程备份密码均 AES-256-GCM 加密落库/落盘，非明文。
  • 认证体系完整：JWT 过期校验 + 用户存在性校验 + 账户锁定（3 次/15 分钟）+ 维护模式拦截；密码 bcrypt 哈希（SALT_ROUNDS=12），注册密码最小长度 8 位。
  • 图片上传防护到位：MIME 白名单、大小限制、随机文件名、目录穿越防护（deleteImageFile 的 startsWith 校验）、background.js 的扩展名白名单 + 路径二次校验，都是范本级实现。
  • 备份链路有校验：上传备份有扩展名白名单 + JSON 结构校验；下载/删除路径经 resolveBackupPath 统一解析（穿越防护），多处调用。
  • 无注入面：全部数据库访问走 Sequelize 参数化（原始 query 均为常量 SQL 或脚本内使用）；IP 探测的 spawn 为数组传参无 shell，不存在命令注入；前端无 dangerouslySetInnerHTML。
  • 前端 token 存储：sessionStorage + PBKDF2(10万次)/AES-GCM 加密，且仅在安全上下文启用，降级路径明确。
  • git 工作区健康：当前未提交改动为正常的在途开发（DeviceCredential/redfish 采集相关），无异常文件。
