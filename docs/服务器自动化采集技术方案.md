# 服务器自动化采集技术方案（草案）

> 状态：讨论稿 v2，待评审
> 方向：**先带外、暂缓 OS 侧**（评审定稿：第一步 Redfish）
> 背景：交换机已完成端口自动化采集（`services/portDiscovery/`，SSH/SNMP/Telnet → 解析 → diff 预览 → apply 落库）。本方案讨论服务器（物理机）的自动化采集如何复用该架构。

## 1. 采集目标与路径

服务器采集目标分两类：**硬件资产清单**（CPU/内存条/硬盘/电源/序列号）与**业务网口**（对齐现有 DevicePort 端口管理）。三条可选路径：

| 路径 | 采集目标 | 不依赖 OS | 前提条件 | 定位 |
|---|---|---|---|---|
| **Redfish**（BMC 带外） | 硬件清单 + 传感器 + 网卡，结构化 JSON | ✅ | BMC 网络可达 + 账号 | **第一步，主路径**，现代机型全覆盖 |
| **BMC SNMP**（BMC 带外） | FRU（序列号/型号）+ 传感器/健康 | ✅ | BMC 开 SNMP 服务 | **第二步**，老机型兜底（iDRAC6/7、iLO3/4 等 Redfish 支持不全的） |
| **OS 侧 SSH**（带内） | 精确硬件清单（dmidecode/lsblk）+ 业务网口 | ❌ | Linux SSH 账号 | 暂缓（复用现有 SSH 驱动，随用随启） |

不采用：Agent 常驻（部署维护成本高，不做）；**OS 侧 SNMP（不做，2026-10-12 确认）**——需逐台装配 snmpd，"免登录"是错觉，收益不成立；Windows 服务器带内采集需 WinRM，暂缓。

### 1.1 能力探测与自动降级（应对 Redfish 未开启）

**问题**：Redfish 不一定所有设备都开启（老机型默认关闭、防火墙拦截 443、账号无 Redfish 权限、仅自签证书等），不能单点依赖，采集必须多路径自动降级。

**降级链**（按优先级逐级尝试，路径 ①② 为带外，③ 为带内兜底）：

| 顺序 | 路径 | 轻量探测方式（5s 级超时） | 探测失败判定 |
|---|---|---|---|
| ① | Redfish | `GET /redfish/v1/ServiceRoot` | 拒连 / 超时 / 404 / 401 → 降级 |
| ② | BMC SNMP | sysDescr GET（复用现有 `SnmpDriver`，net-snmp） | 超时 / no response → 降级 |
| ③ | OS 侧 SSH | 登录 + `ip -j link`（复用现有 ssh2 驱动） | 连接失败 / 命令不存在 → 报诊断 |

**关键机制**：

1. **探测而非盲试**：每条路径先做轻量探测，失败立即降级不阻塞；探测结果缓存到凭据现有字段 `testStatus` / `testMessage`，下次采集直接从上次成功路径开始，避免每次都全链路试错。
2. **路径组合而非互斥**：同一设备可"Redfish 关但 SNMP 开"——硬件清单与业务网口可来自不同路径，结果做**字段级合并**（如硬件清单走 ②、网口走 ①或③）。
3. **全路径失败 ≠ 采集失败**：返回结构化诊断（各路径失败原因：超时/认证/命令不存在），前端引导补凭据或开启 BMC 服务，而非笼统报"采集失败"。
4. **凭据按路径独立**：①② 用 BMC 地址+账号（② 另需 community），③ 用 OS 账号，分别在凭据管理中配置；缺哪条凭据即跳过对应路径。
5. **BMC 可达性已确认**（见 §5.2），故 ①② 失败大概率是服务/账号问题而非网络问题，诊断信息应优先指向这两者。

## 2. 关键结论（讨论共识）

1. **网口采集与硬件清单是两条线**：网口走现有 DevicePort diff + apply 流程；硬件清单进设备详情/动态字段，不塞端口表。
2. **BMC 带外采集不需要 OS**：Redfish 与 BMC SNMP 均走 BMC 管理口，机器关机可采；两者凭据可共用（BMC 地址 + 账号，SNMP 另需 community）。**带外是本方案优先方向。**
3. **BMC 上的 IF-MIB 只有 BMC 管理口自身**，采不到业务网口；业务网口将来若需带内采集，走 OS 侧 SSH / Redfish。
4. **BMC SNMP 是 per-vendor 私有 MIB**（DELL-RAC-MIB、CPQHLTH-MIB 等），需按厂商写映射——与现有 `DRIVERS` 按厂商注册的结构一致。
5. **OS 侧 SNMP 不做（2026-10-12 确认）**：技术上可行（现有 `SnmpDriver` 只依赖 IF-MIB，仅需虚拟接口过滤）且近乎零新代码，但需逐台装配 snmpd，"免登录"是错觉，运维收益不成立。结论记录在此，若后续需求变化可随时启用，无返工成本。

## 3. 架构接入方式

复用现有 portDiscovery 架构（凭据 → 驱动 → 解析 → diff → apply），新增最小改动：

- `DeviceCredential.protocol` 增加 `redfish`；BMC 地址复用 IP 字段或新增 `bmcAddress`
- 新建 `services/serverDiscovery/`，驱动按协议/厂商分：`redfish.js`（协议级，第一步）、`bmcSnmp/<vendor>.js`（老机型，第二步按需）
- 采集结果分流：
  - 硬件清单 → 更新设备详情 / 动态字段（落库目标待评审确认）
  - 网卡端口 → 走现有 DevicePort diff + apply（Redfish 可获取网卡信息，带外即可覆盖）
- 厂商识别：Redfish `Manufacturer` 字段直出，无需探测

## 4. 实施路线

| 阶段 | 内容 | 说明 |
|---|---|---|
| 第一步 | Redfish 采硬件清单 + 网卡 | 主路径：结构化 JSON 无需解析器，覆盖现代机型；需确认 BMC 网络可达 |
| 第二步 | BMC SNMP 补老机型 | 按实际老机型品牌按需开发 per-vendor 驱动（iDRAC6/7、iLO3/4 等） |
| 暂缓 | OS 侧 SSH 带内采集 | 技术结论已验证（§2），需要时随时启用，无返工成本；OS 侧 SNMP 已确认不做（§2.5） |
